# Эксплуатация TranscriptBot v1

Рабочий запуск и восстановление на действующем сервере выполняются после
согласования с владельцем. Команды ниже — инструкция, а не свидетельство
выполненного развёртывания. Требуются Docker Compose, свободное место на томах
и уже подготовленный защищённый `.env`; значения ключей в журналы не выводить.

## Первый запуск и обновление

1. Убедиться, что другой экземпляр этого бота не выполняет polling. Проверить
   список разрешённых пользователей и доступность исходящих Telegram/Groq/HTTPS.
   Bot API слушает только сеть Compose, порты на хост не публикуются.
2. Собрать образы и проверить конфигурацию:

   ```bash
   docker compose config --quiet
   docker compose build
   python3 scripts/check_containers.py
   ```

3. На существующей установке сначала остановить bot и worker, сохранить снимок
   данных, затем выполнить миграции. Для первого запуска снимок ещё не требуется:

   ```bash
   docker compose run --rm --no-deps worker migrate
   docker compose run --rm --no-deps worker worker --check
   docker compose run --rm --no-deps bot bot --check
   docker compose up -d
   docker compose ps
   ```

   Если том Telegram ещё не инициализирован, сначала создать контейнер Bot API:
   его образ создаёт каталог с UID/GID `10001:10001`. Все тома должны быть
   доступны этому пользователю. На обновлении миграции применяются явно;
   несовместимая схема блокирует старт приложения.

4. Проверить диагностику обоих процессов и ошибки безопасных журналов:

   ```bash
   docker compose exec worker transcriptbot healthcheck --service worker
   docker compose exec bot transcriptbot healthcheck --service bot
   docker compose logs --tail=100 bot worker
   ```

   Heartbeat обновляется каждые 5 секунд, в том числе во время скачивания и
   ожидания Groq. Возраст больше 60 секунд даёт ненулевой healthcheck.
   Compose проверяет процессы раз в 30 секунд; для Bot API проверяется локальный
   TCP listener. Это проверка жизнеспособности процессов, а не обещание
   доступности внешних сервисов. Docker сам по себе не перезапускает контейнер
   только из-за статуса unhealthy: оператор проверяет причину перед перезапуском.

## Очистка и диск

- После подтверждения превью, TXT и JSON worker удаляет содержательные файлы.
  После отмены сначала прекращается активная операция, затем удаляются файлы.
  Отдельная корутина проверки TTL работает и во время длительного скачивания;
  общий Telegram-кеш защищён во время получения нового Telegram-файла,
  когда его локальный путь ещё неизвестен.
  Метаданные истории и подтверждённые Telegram message ID остаются в SQLite.
- Ошибочные задания сохраняются 7 дней. Проверка TTL выполняется при старте и
  каждые `CLEANUP_INTERVAL_SECONDS` (по умолчанию 600). После истечения TTL
  продолжение отключается атомарно, затем удаляются файлы.
- Ошибка удаления сохраняет `cleanup_pending`; повтор — через заданный интервал
  или при следующем запуске. Доставка и распознавание не повторяются.
- Telegram-кеш удаляется только по учтённым путям в каталогах медиа TDLib.
  Общий файл сохраняется для других удерживающих его заданий, включая очередь
  с тем же Telegram file ID. Служебная база Bot API, неизвестные каталоги,
  символьные ссылки и пути за пределами разрешённых корней не удаляются.
- При старте worker убирает незавершённые `.part` и текущий WAV известных заданий,
  сверяет сохранённые источники и ответы. Сбой между публикацией ответа и
  фиксацией SQLite восстанавливает опубликованный ответ без нового Groq.
  Недостающие файлы позднего этапа дают `recovery_files`, освобождая FIFO.
- Перед новой загрузкой требуется место для исходника, WAV, результатов и
  `DISK_RESERVE_BYTES` (по умолчанию 1 ГиБ). Ошибочные задания не удаляются раньше
  TTL ради новых загрузок. При нехватке места оператор освобождает посторонние
  данные или расширяет диск; сохранённые результаты можно доставить и очистить.

JSON диагностики содержит размеры очереди, ID/этап/возраст текущего задания,
остаток ожидания, свободные байты каждого тома, состояние места для новой
загрузки, количество ожидающих очистку заданий и ошибок очистки. В нём нет
ссылок, ключей и текста расшифровок. `healthy` отражает heartbeat; недостаток
места или ошибки очистки отображаются отдельно и требуют внимания оператора.

## Резервное копирование

`transcriptbot backup --output /absolute/path/snapshot.sqlite3` использует
SQLite backup API и проверяет целостность, foreign keys и миграции. Целевой
файл создаётся с правами 0600 и никогда не перезаписывается. Команда может
копировать работающую базу с WAL, но такая копия **не содержит медиафайлы**.

Для восстановления незавершённых заданий нужен согласованный снимок трёх
томов. Остановить все три сервиса перед копированием, чтобы worker не удалил
файлы, а Bot API не изменил свой кеш и служебную базу. Хранить резервные копии
защищённо: они содержат исходные ссылки, Telegram ID и временное содержимое.
Каталог `backups/` исключён из Git. Подготовить новый пустой каталог снимка,
доступный UID 10001 с правами 0700, и подставить его абсолютный путь вместо `/srv/tb-backup`:

```bash
docker compose stop bot worker telegram-bot-api
docker compose run --rm --no-deps --volume /srv/tb-backup:/backup \
  worker backup --output /backup/transcriptbot.sqlite3
docker compose run --rm --no-deps --volume /srv/tb-backup:/backup \
  --entrypoint python worker -c \
  'import tarfile; t=tarfile.open("/backup/work.tar", "x"); t.add("/work", arcname="work"); t.close(); t=tarfile.open("/backup/telegram.tar", "x"); t.add("/telegram", arcname="telegram"); t.close()'
docker compose start telegram-bot-api bot worker
```

Каталог назначения должен быть новым: существующие снимки не перезаписываются.
Зафиксировать версию Git/образа рядом со снимком. Секреты сохраняются отдельно
по правилам владельца; описанные команды их не копируют.

## Восстановление

1. Проверить снимок и версию приложения. Подготовить **новые пустые тома** с
   UID/GID 10001; существующие рабочие тома не удалять и не перезаписывать.
   Все три сервиса восстановленного экземпляра пока должны быть остановлены.
2. Восстановить доверенные архивы work и telegram в соответствующие пустые
   тома, сохранив пути `/work/jobs` и `/telegram`. При использовании Python
   tarfile применять `filter="data"`; архивы не должны выходить за корни томов.
   Рабочие манифесты содержат абсолютные пути, поэтому смена этих путей без
   согласованной миграции не поддерживается.
3. Подключить снимок только для чтения и выполнить:

   ```bash
   docker compose run --rm --no-deps --volume /srv/tb-backup:/backup:ro \
     worker restore --input /backup/transcriptbot.sqlite3
   docker compose run --rm --no-deps worker migrate
   ```

   `restore` отказывается работать, если целевая SQLite или её WAL/SHM уже
   существуют. Схема копии должна соответствовать образу; старый снимок сначала
   восстанавливают совместимым образом и затем отдельно обновляют с миграциями.
   Устаревшие heartbeat при восстановлении очищаются.
4. Убедиться, что прежний экземпляр остановлен. Запустить восстановленный,
   проверить healthcheck, очередь, статус текущего задания и ошибки очистки.
   Источник и контрольные точки сверяются; сохранённые части не распознаются
   повторно. Незавершённая доставка использует отдельные подтверждения файлов.
   Откат к старому снимку может повторить внешние запросы, сделанные после него.

## Приёмка

Автономный набор запускается `python3 scripts/check_containers.py` с вымышленными
ключами, без внешней сети и на удаляемых тестовых томах. Он проверяет установленный
пакет, restart, завершение процессов, пять миграций, крупный `getFile` на
подставном HTTP API, очистку и повторное скачивание, сохранение служебных данных,
снимок SQLite с рабочими файлами, восстановление и heartbeat.

Подставной API не подтверждает реальное поведение TDLib. Перед эксплуатационной
готовностью v1 отдельно требуется живой Telegram-файл больше 20 МБ: `getFile`,
обработка, подтверждённая выдача, удаление учтённого кеша и повторный `getFile`
с проверкой размера/SHA-256. Для этой проверки нужен доступный боту файл и
изолированный тестовый кеш, чтобы не затронуть действующие задания.
Живые direct/YouTube/вложенный Mail.ru и синтетическая речь Groq уже проверены
в этапах 4–5; результаты находятся в `docs/handoffs/`.

Официальный сервер при `getFile` вызывает TDLib `downloadFile`; одного чтения
локального пути нет. Основание для проверки повторного скачивания —
[закреплённый Client.cpp](https://github.com/tdlib/telegram-bot-api/blob/e3e9dd8e5b3d7ab8537cd5a10dc31d5ffa8f82d1/telegram-bot-api/Client.cpp#L15884).
Окончательное подтверждение этого сценария даёт живой gate.

## Изменения после аудита 2026-10-09

- Перед переходом на образы `transcriptbot-app:audit` и
  `transcriptbot-bot-api:audit` при остановленных сервисах сделать backup,
  затем выполнить существующую команду `transcriptbot migrate`: теперь **5**
  миграций. Автоматического развёртывания аудит не выполняет.
- Контейнеры используют Python 3.12.15 / Debian 13, FFmpeg 9.0.2 из проверенного
  официального исходника. FFmpeg собран без сетевых протоколов; Deno/EJS
  остаётся для YouTube. Образ приложения не содержит всей системной codec/GUI
  цепочки Debian FFmpeg. Runtime использует отдельный security snapshot
  9 октября, liblzma5 5.8.1-1+deb13u2; неиспользуемый pip отсутствует.
- Ограничения Compose: bot 512 MiB RAM, worker/API по 2 GiB, 2 CPU и 128 PID
  на сервис; tmpfs /tmp 256 MiB; логи 3 файла по 10 MiB. Для более тесного хоста
  размеры нужно подобрать по нагрузке, сохранив запас для длинных заданий.
- У bot теперь собственный flock, как у worker. Второй процесс той же роли
  отклоняется до polling/API-вызовов. На каждый используемый для доставки job
  создаётся пустой lock-файл рядом с SQLite; не удалять их при работающих
  сервисах. Worker не удаляет содержимое задания до остановки его Telegram I/O.
- Backup/restore ограничен 60 секундами; при блокировке базы или медленном
  диске команда завершится безопасной ошибкой, существующие базы сохранятся.
- До 10 ожидающих служебных ответов на чат, не более 1000 суммарно; обычные
  reply не задерживают готовые операции заданий. Под нагрузкой лишний reply/callback
  не ставится в очередь, но входящий update и сама команда фиксируются.
- Диагностика inbox и завершённые служебные reply/callback очищаются после
  30 дней порциями до 1000 строк за обслуживание. Pending outbox, jobs и
  подтверждения доставки результатов по заданию сохраняются. Старый update
  ниже committed offset не выполняется заново даже после удаления inbox-строки.
- [Отчёт аудита](../handoffs/security-audit-2026-10-09.md) содержит найденные
  дефекты, проверки и остаточные системные CVE. Живая Telegram-приёмка из
  этапа 6 всё ещё требуется отдельно.
