# Технический план реализации TranscriptBot v1

## 1. Исходное состояние и подход

На момент составления плана в проекте была только [спецификация](../specs/transcriptbot-v1.md). Прикладного кода, зависимостей и инфраструктуры не было. **Конфликтов существующей архитектуры со спецификацией не обнаружено.**

Из соседнего `groq_transcript` перенести алгоритмы поиска пауз, подготовки WAV и объединения сегментов вместе с соответствующими тестами. Его 11 тестов сейчас проходят. CLI целиком не использовать: синхронное выполнение, завершение при 429, проверка формата по расширению и преобразование JSON единственной части противоречат требованиям бота.

Реализовать один Python-пакет с двумя точками запуска: `transcriptbot bot` и `transcriptbot worker`. Бот отвечает за Telegram, приём запросов и доставку результатов; worker — за скачивание, обработку и очистку. Общение между процессами — через SQLite и ссылки на рабочие файлы.

Целевой файл плана при сохранении: `docs/plans/transcriptbot-v1-implementation.md`.

|---|---|

| 3. Telegram | **Завершён**: 155 тестов, статические проверки, HTTP-транспорт на подставном API, сборка приложения и автономные контейнерные проверки прошли |
| 4. Загрузчики | **Завершён**: защищённые загрузчики, автономные проверки и живые direct/YouTube/вложенный Mail.ru прошли; домен datacloudmail.ru подтверждён пользователем |

После завершения каждого этапа выполняются соответствующие и полные доступные
проверки, создаются локальные коммиты и работа останавливается до указаний
пользователя. Полноценный запуск и push требуют отдельного согласования.

## 2. Порядок реализации

### Этап 1. Каркас и воспроизводимое окружение — завершён 2026-10-08

- Создать пакет в `src/transcriptbot`, `pyproject.toml`, lock-файл uv, настройки pytest и Ruff.
- Разделить код на конфигурацию, хранилище, Telegram-интерфейс, загрузчики, обработку медиа, Groq-адаптер и worker.
- Реализовать проверку конфигурации при запуске. Неверные настройки завершают процесс до начала polling или обработки.
- Подготовить общий Python-образ и Compose с тремя сервисами. FFmpeg, FFprobe, yt-dlp и Deno включить в образ worker.
- Зафиксировать зависимости и образ Telegram Bot API; исключить автоматическое обновление во время работы.

**Результат:** оба процесса запускаются, проверяют окружение и корректно завершаются по SIGTERM.

### Этап 2. SQLite, очередь и переходы состояний — завершён 2026-10-08

- Добавить версионированные SQL-миграции; выполнять их отдельной командой перед запуском сервисов.
- Использовать `sqlite3` через выделенный поток доступа в каждом процессе; включить WAL, foreign keys, busy timeout и `synchronous=FULL`.
- Создание задания, проверку лимитов, назначение позиции и регистрацию Telegram update выполнять одной транзакцией `BEGIN IMMEDIATE`.
- Порядок очереди задавать монотонным номером. Ручное продолжение присваивает новый номер, сохраняя ID задания и готовые части.
- Защитить worker файловой блокировкой на общем томе. При старте восстанавливать единственное активное задание раньше новых.
- Хранить этап, счётчик попыток и `next_attempt_at`, чтобы ожидание переживало перезапуск.
- Все переходы выполнять условными обновлениями состояния; отмена не должна быть перезаписана поздним ответом API.

**Результат:** очередь проверяется без Telegram и Groq на временной базе, включая конкурентное поступление запросов и восстановление.

**Уточнения реализации:** `transcriptbot migrate` применяет SQL-миграции с проверкой
версий и SHA-256 в одной транзакции, без `executescript` (он мог бы разорвать
транзакцию). Бот и worker открывают только уже мигрированную базу. Для доступа
используется `ThreadPoolExecutor(max_workers=1)` и одно соединение на его потоке.
Состояние (`queued`, `active`, `retry_wait`, `quota_wait`, `failed`, `cancelled`,
`completed`) хранится отдельно от этапа (`download`, `prepare`, `transcribe`,
`assemble`, `deliver`). Частичный UNIQUE-индекс допускает только одно активное
или ожидающее задание. `revision` защищает от поздних результатов операций,
`generation` — от повторного управления старыми кнопками после продолжения.
Обработанные update и исходный результат callback сохраняются бессрочно;
продвижение polling offset и sender подключаются в этапе 3.
В схеме уже есть `chunks`, `assets`/`job_assets`, `outbox`, `polling_state`;
текст и ответы Groq в неё не записываются. На этом этапе worker восстанавливает
метаданные активного задания, но ещё не выполняет медиа-операции.

### Этап 3. Telegram-приём и надёжная доставка — завершён 2026-10-08

- Создать aiogram routers и общий сервис преобразования сообщений в запрос задания. Проверку инициатора использовать также в командах истории и callback-кнопках.
- Реализовать собственный цикл `getUpdates` через aiogram Bot. Перед продвижением сохранённого offset транзакционно фиксировать обработку update и созданное задание либо решение об отказе.
- Обработчики не должны скачивать файлы или ждать распознавания. Ответы пользователю регистрировать в SQLite для отдельной отправки.
- Добавить sender-корутину внутри процесса бота: создание и изменение статуса, превью, отправка TXT/JSON, обработка Telegram 429.
- Для каждого результата сохранять отдельную отметку доставки. Повторять только неподтверждённую операцию.
- Обновления прогресса объединять до последнего значения; сообщения одного чата отправлять с ограничением частоты.
- Хранить исходные message ID и topic ID. Если статус удалён, создавать замену; если тема или чат недоступны, фиксировать ошибку доставки, сохраняя результат для продолжения.

Обычный polling aiogram по умолчанию запускает обработчики отдельными задачами; поэтому подтверждение updates необходимо контролировать явно. [Исходники dispatcher](https://docs.aiogram.dev/en/latest/_modules/aiogram/dispatcher/dispatcher.html).

**Результат:** сценарий «принять → сохранить → перезапустить → выдать статус» работает без потери задания.

**Уточнения реализации:** routers только разбирают сообщение в `Request` без внешнего
I/O. `TelegramStore.accept` одной транзакцией сохраняет решение, изменение очереди,
ответы в outbox и следующий offset. Для этого операции создания/отмены/продолжения
репозитория получили синхронные методы для использования внутри общей транзакции;
их прежние асинхронные интерфейсы сохранены. Polling обрабатывает updates последовательно.

Миграция 002 расширяет outbox для ответов без задания и callback-подтверждений,
сохраняя прежние отметки файлов; сохраняет ID исходного сообщения отдельно от
инициирующей команды и таблицу ограничений отправок чата. Sender внутри bot
использует собственный Bot API, обновляет статус не чаще 5 секунд, объединяет
прогресс и восстанавливает удалённый статус. Ответ `/status` также содержит кнопки.

Preview/TXT/JSON регистрируются через `TelegramStore.enqueue_results` для активного
этапа `deliver`. Файлы находятся в `WORK_DIR/<job_id>/`; превью читается из TXT
при отправке. Подтверждения старого поколения сохраняются при продолжении,
поэтому повторяется только неподтверждённая доставка. Завершение проверяется
после подтверждения превью и обоих файлов; физическая очистка остаётся этапом 6.

429 сохраняет срок следующей попытки и ограничение чата, не расходуя обычные повторы.
Сетевые/серверные и некорректные ответы API повторяются пять раз по сохранённому
расписанию. Недоступный чат/тема или исчерпание повторов фиксируют ошибку и освобождают
очередь. При недоступном статусе управлять заданием можно через новый `/status`.
Подставные HTTP-проверки проверяют реальный multipart и остановку long polling;
рабочие сервисы и живые Telegram-запросы на этом этапе не запускались.

### Этап 4. Загрузчики и проверка медиа — завершён 2026-10-08

- Создать общий сетевой транспорт HTTPX поверх HTTPcore с проверкой DNS и соединением непосредственно с проверенным IP. Сохранить исходное имя для TLS и HTTP Host; отключить прокси из окружения.
- Реализовать прямую загрузку потоком в `.part`. Проверять фактическое число байтов; готовый файл публиковать атомарным переименованием.
- Для Mail.ru корректно извлекать весь путь после `/public/`, получать сервер скачивания через dispatcher, проверять его домен и скачивать с Referer исходной страницы. Фикстуры должны содержать вложенные пути и percent-encoding.
- Для YouTube запускать собственный дочерний процесс-обёртку над yt-dlp. Подключить единственный защищённый `RequestHandler`; запрещать обход через другие сетевые обработчики и внешние загрузчики. Использовать встроенный загрузчик и локально установленный JavaScript solver.
- Для Telegram вызывать `getFile` только при наступлении очереди. Полученный локальный файл учитывать как ресурс Bot API, не создавая обязательную вторую копию.
- После скачивания вычислять SHA-256, получать данные FFprobe и создавать неизменяемый манифест источника.
- До следующего этапа проверить Mail.ru на предоставленной ссылке и YouTube на целевом сервере. Несовместимость источника фиксировать как препятствие приёмке, а не обходить отключением защиты.

HTTPcore позволяет задавать сетевой backend, а yt-dlp — собственный обработчик запросов. [HTTPcore](https://www.encode.io/httpcore/network-backends/), [yt-dlp](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/networking/common.py).

**Результат:** каждый источник выдаёт проверенный локальный файл либо типизированную ошибку.

**Состояние реализации на 2026-10-08:** этап завершён. Прямая ссылка, YouTube
и предоставленный вложенный файл Mail.ru успешно скачаны на текущем сервере.
Пользователь подтвердил домен `datacloudmail.ru`; спецификация и allowlist
обновлены для него и его поддоменов. HTTPS, DNS/IP, TLS и проверка каждого
перенаправления сохранены. Mail.ru: 944 416 750 байт, 1818,958367 секунды,
AAC, первая аудиодорожка 1; SHA-256 и FFprobe проверены.

**Уточнения реализации:** общий синхронный HTTPX/HTTPcore транспорт используется
в управляемом дочернем процессе для direct/Mail.ru/YouTube. Это позволяет остановить
DNS, скачивание и всю группу FFprobe/Deno без передачи ключей. DNS имеет отдельный
срок ожидания; IP проверяется один раз перед числовым соединением, исходный Host/SNI
сохраняется. HTTPX-пул и SyncStream подключены через изолированный адаптер для
закреплённых версий библиотек, поскольку HTTPX не предоставляет публичного
аргумента `network_backend`.

yt-dlp содержит только один RequestHandler; загрузка выбранной HTTP(S)-аудиодорожки
выполняется прямым вызовом встроенного HttpFD. Диспетчер HLS/DASH/FFmpeg/внешних
загрузчиков не используется. Лимит байтов суммарный для range-запросов, EJS
установлен локально, удалённые компоненты отключены.

Ограничения FFprobe на протоколы/демультиплексоры из этапа 5 применены уже здесь:
загрузчик должен проверять полученное медиа безопасно. Подготовка аудио и вызовы
Groq остаются этапом 5. `source.json` публикуется с fsync без перезаписи существующего
манифеста; восстановление сверяет SHA-256. Ресурсы, включая `.part` и Bot API кеш,
связаны с заданием в существующих assets/job_assets; миграции не потребовались.
`finish_download` условно и атомарно сохраняет метаданные и этап `prepare`.
Worker выполняет только `download`; активный `prepare` удерживает FIFO до этапа 5.

Подробности и воспроизводимые команды — [проверки этапа 4](../handoffs/stage-4-validation.md).

### Этап 5. Медиа-конвейер и Groq

- Перенести планирование частей в самостоятельный модуль. Границы хранить в целых отсчётах 16 кГц, переводя их в секунды только для API и JSON.
- Управлять FFmpeg/FFprobe через subprocess с таймаутами, ограниченным выводом и завершением всей группы процессов при отмене.
- Разрешать только локальные входы и необходимые демультиплексоры; запретить сетевые протоколы, HLS, concat и внешние ссылки из контейнеров.
- Создавать WAV только текущей части. Проверять размер до вызова Groq; не сохранять полный промежуточный WAV всей записи.
- Использовать `AsyncGroq(max_retries=0)`. Повторами управляет worker, чтобы исключить вложенные циклы повторов SDK. [Groq SDK](https://github.com/groq/groq-python#retries).
- Сохранять полный JSON ответа части в отдельный файл через запись, `fsync` и атомарное переименование; затем фиксировать его путь и контрольную сумму в SQLite.
- При восстановлении принимать уже опубликованный корректный ответ, даже если процесс упал до обновления SQLite.
- Для единственной части сохранять исходный объект ответа; для нескольких запускать отдельную сборку. TXT и итоговый JSON публиковать атомарно.

**Результат:** конвейер восстанавливается между любыми двумя частями и перед доставкой результатов.

### Этап 6. Очистка и эксплуатационная готовность

- Добавить очистку после доставки, отмены и окончания срока хранения ошибочного задания.
- Учёт файлов Bot API вести отдельно от каталога задания. Удалять кеш только при отсутствии пользователей ресурса; не затрагивать служебную базу сервера.
- После доставки отмечать необходимость очистки отдельно: ошибка удаления вызывает повтор очистки, но не повторную отправку или распознавание.
- Добавить startup-reconciliation: сверка базы с манифестами, удаление незавершённых временных файлов и завершение прерванной очистки.
- Подготовить healthcheck, резервное копирование SQLite через backup API, восстановление, инструкции первого запуска и диагностики.

## 3. Данные и внутренние интерфейсы

| Сущность | Что хранит |
|---|---|
| `jobs` | Источник, владелец, адрес доставки, очередь, этап, попытки, сроки и код ошибки |
| `chunks` | Границы, состояние, путь и хеш сохранённого ответа |
| `assets` | Рабочие файлы и ресурсы кеша Bot API, ссылки использующих заданий |
| `outbox` | Операции отправки, сроки повторов и подтверждённые message ID |
| `polling_state` | Подтверждённый offset и обработанные update ID |
| `schema_migrations` | Версия структуры базы |

Текст транскрипции и ответы Groq хранить в файловом рабочем каталоге, а не в SQLite. Outbox для превью ссылается на TXT; содержимое сообщения формируется непосредственно перед отправкой.

Зафиксировать типы `SourceRef`, `MediaInfo`, `ChunkPlan`, `ArtifactRef`, `JobError` и `RetryDecision`. Основные интерфейсы:

- Загрузчик: `fetch(source, workspace, cancellation) → DownloadedMedia`.
- Медиа-сервис: `probe`, `plan_chunks`, `extract_chunk`.
- Groq-адаптер: `transcribe(path) → raw_json`.
- Репозиторий: создание, получение следующего задания, условный переход этапа, отмена и продолжение.
- Сборщик: `assemble(manifest, responses) → ResultArtifacts`.

HTTP API не добавлять. Команды запуска, Telegram-команды и формат файлов являются внешними интерфейсами проекта.

## 4. Ошибки, ограничения и технические defaults

- Разделить ошибки на временные, ожидание квоты и окончательные. Для временных использовать пять повторов с задержками 5, 15, 45, 135 и 300 секунд.
- Для квоты сохранять дату следующей проверки: `Retry-After` имеет приоритет; без него — 60, 120, 240 секунд с дальнейшим увеличением до часа. Ожидание квоты не расходует пять обычных повторов.
- Успешные и неопределённые запросы учитывать в журнале расхода аудио консервативно; опубликованные квоты использовать как настраиваемый предварительный ограничитель, ответы Groq — как окончательный источник решения.
- Перед каждой новой операцией и после её завершения проверять отмену. Поздний ответ отменённого задания не публиковать.
- При ошибке части или доставки продолжение возобновляет соответствующий этап. После удаления файлов через 7 дней кнопка продолжения недоступна: пользователь отправляет источник заново.
- Размеры считать в десятичных байтах: вход — `2_000_000_000`, загрузка Groq — `25_000_000`; для подготовленного WAV оставить запас до `24_500_000`.
- Сетевые defaults: connect 10 секунд, ожидание данных 60 секунд, максимум 5 перенаправлений, общий срок скачивания 60 минут. Groq — 300 секунд на запрос; FFprobe — 60 секунд, подготовка части — 300 секунд.
- Перед загрузкой резервировать место для исходника, текущей части и результатов с запасом 1 ГиБ. Не удалять ошибочные задания раньше срока ради новой загрузки.
- Ограничить права каталогов и базы; запускать сервисы без root. В дочерние процессы не передавать ключ Groq и Telegram-токен.
- Журналы содержат ID, этап, длительность операции и код ошибки. Полные URLs, тела API-ответов и необработанный вывод библиотек в них не включать.

## 5. Проверки и завершение

Проверять каждый этап до подключения следующего:

- **SQLite:** конкурентное создание при лимитах, повтор update, FIFO, отмена, повторные callback и восстановление активного задания.
- **Загрузчики:** IPv4/IPv6, смешанные DNS-ответы, DNS rebinding, опасные redirects, превышение размера без Content-Length, неверный TLS, вложенный путь Mail.ru и отсутствие обхода транспорта в yt-dlp.
- **Медиа:** синтетические записи с паузами и непрерывной речью, первая аудиодорожка, полный охват отсчётов, короткий хвост, размеры WAV и запрет сетевых обращений FFmpeg.
- **Groq и сборка:** подставные ответы, пустой текст, сохранение исходного JSON одной части, глобальные времена нескольких частей, 429 и сбой между записью ответа и фиксацией прогресса.
- **Доставка и очистка:** частично отправленный результат, потерянный ответ Telegram, удалённый статус, недоступная тема, отмена во время запроса, ошибка unlink и повторное скачивание очищенного Telegram-файла.
- **Контейнеры:** остановка и повторный запуск сервисов на разных этапах, сохранность томов, backup/restore, нехватка места.
- **Живые проверки:** крупное вложение Telegram, YouTube, предоставленный Mail.ru URL, прямая ссылка и короткая синтетическая запись через Groq.

Для долгих ожиданий использовать управляемые часы в тестах; квоты и четырёхчасовые записи проверять преимущественно подставными API.

В эксплуатационные проверки включить возраст текущего задания, срок ожидания квоты, размер очереди, свободный диск, heartbeat worker и ошибки очистки. Реализация считается завершённой после прохождения соответствующих критериев спецификации, включая реальную загрузку Mail.ru и очистку кеша Bot API. Развёртывание на рабочем сервере выполняется отдельно после согласования.
