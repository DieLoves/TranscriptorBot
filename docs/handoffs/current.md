# Handoff

Дата: 2026-10-08. Проект: `/home/dev/workspace/projects/transcriptbot`.

## Objective

Реализовать Telegram-бота транскрипции через Groq по спецификации v1.
После каждого этапа выполнить соответствующие и полные доступные проверки,
создать локальный коммит и остановиться до указаний пользователя.
Push и рабочее развёртывание требуют отдельного согласования.

## Current state

- **Этапы 1–3 завершены**. Спецификация и её scope не изменены; этап 4 не начат.
- Есть конфигурация, CLI `transcriptbot bot`, `worker`, `migrate`, `--check`,
  uv.lock, Docker/Compose с тремя сервисами, валидация окружения и сигналы остановки.
- SQLite/WAL использует выделенный поток/соединение в каждом процессе,
  foreign keys, busy timeout 10 секунд, `synchronous=FULL` и защищённые файлы.
- SQL-миграции с SHA-256 применяются отдельной командой. Теперь их две;
  сервисы отказываются запускаться без актуальной схемы.
- Приём Telegram update, создание/отмена/продолжение задания, проверка лимитов,
  ответы в outbox и следующий polling offset фиксируются одной транзакцией.
  Повтор update возвращает первоначальное решение и не дублирует ответ/задание.
- Приём через aiogram routers: вложения пяти типов, отдельные ссылки,
  `/transcribe` с аргументом/ответом/именем бота, `/start`, `/help`, `/jobs`, `/status`.
  В группах обычные сообщения игнорируются, доступ проверяется по инициатору.
  Анонимные команды отклоняются. История/статусы/кнопки ограничены владельцем
  и в группе — исходным чатом. Сохраняются команда, исходный message ID и тема.
- `bot` теперь подключается к собственному Bot API в режиме local, выполняет
  последовательный long polling и отправку из outbox отдельной корутиной.
  `--check` и миграции остаются автономными и не вызывают API.
- Sender создаёт/редактирует одно сообщение статуса, объединяет прогресс,
  показывает очередь, этап, часть N/M, ожидание квоты и ошибки на русском.
  Обновления — не чаще 5 секунд, включая смену поколения при продолжении.
  Для чата сохранено ограничение: минимум 1 секунда в личке, 3 в группе.
  Callback-подтверждения имеют приоритет и не ждут ограничения сообщений.
- Удалённый статус заменяется. `/status` также содержит кнопки управления.
  Недоступный чат/тема или исчерпание повторов сохраняют ошибку и освобождают очередь.
- Preview/TXT/JSON имеют отдельные отметки доставки; подтверждённые файлы не
  отправляются повторно при перезапуске/продолжении. Превью читается из TXT перед
  отправкой, максимум 3000 символов. Пустой текст всё равно даёт TXT и JSON.
  Файлы доступны только из `WORK_DIR/<job_id>/`, имена очищены и содержат ID.
- 429 сохраняет Retry-After и ограничение чата, не расходуя обычные повторы.
  Сетевые/серверные и некорректные ответы API повторяются до пяти раз с задержками
  5/15/45/135/300 секунд. Тела ответов/секреты/URLs в логи не выводятся.
- Очередь остаётся FIFO, ожидание текущего задания блокирует последующие.
  Продолжение сохраняет ID/этап/части/подтверждения и ставит задание в конец.
  revision защищает от позднего изменения состояния, generation — от старых кнопок.
  Отмена блокирует последующие результаты, уже выполнявшийся запрос может завершиться.
- Worker удерживает файловую блокировку и читает сохранённое активное задание;
  скачивание и распознавание пока не выполняет. Полноценный бот v1 ещё не готов.
- Рабочие сервисы не запущены. `.env` не изменён, права 0600, исключён из Git;
  ключи повторно не запрашивать. Push не выполнялся.

## Key decisions and relevant files

- Спецификация: `docs/specs/transcriptbot-v1.md`; план:
  `docs/plans/transcriptbot-v1-implementation.md`. Этап 3 отмечен завершённым.
- `telegram/requests.py` — Request, разбор источников и routers;
  `polling.py` — контролируемый getUpdates; `store.py` — атомарный inbox/outbox;
  `sender.py` — доставка; `presentation.py` — интерфейс; `__init__.py` — runtime.
- Миграция `002_telegram.sql`: outbox с nullable job_id, reply/callback, UI payload,
  chat_send_state, last_sent_at/status_revision и source_message_id в jobs.
  UI payload содержит только служебный текст, транскрипция остаётся в файлах.
- Синхронные `create_job_in_transaction`, `cancel_in_transaction`,
  `resume_in_transaction` используются внутри транзакции TelegramStore;
  исходные асинхронные методы репозитория сохранены.
- Для будущего worker: опубликовать результаты в `WORK_DIR/<job_id>/`, перейти
  в активный `deliver`, вызвать `TelegramStore.enqueue_results(expected, txt=...,
  verbose_json=...)`. Sender завершает задание после превью и обоих файлов,
  отмечает cleanup_pending; worker этапа 6 выполняет физическую очистку.
- Подтверждения прежнего поколения сохраняются; при resume старые pending
  операции отменяются. Потерянный ответ внешнего API допускает повторную доставку.
- Сервисы требуют отдельного `transcriptbot migrate`; в Compose:
  `docker compose run --rm --no-deps worker migrate` перед запуском.
- `scripts/check_telegram_offline.py` — контейнерный сценарий с подставным API;
  в host тесты находятся в `tests/test_telegram.py`.
- Python 3.12; aiogram 3; Groq `whisper-large-v3-turbo`; один worker;
  Redis/HTTP API приложения нет. Конвейер, загрузчики и очистка — последующие этапы.
