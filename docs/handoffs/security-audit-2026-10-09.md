# Аудит TranscriptBot v1 — 2026-10-09

Статус: локальный аудит и все автономные проверки завершены. Остаточные
системные замечания без исправлений Debian и живая Telegram-приёмка открыты.
Проверены все production-модули, миграции, настройки, Docker/Compose,
эксплуатационные команды и существующие тесты. Спецификация v1 сохранена.

## Подтверждённые проблемы и исправления

| Проблема | Последствие | Исправление / проверка |
|---|---|---|
| Worker удалял результаты отменённого задания, пока bot ещё читает файл для отправки | Ошибка действующей загрузки, гонка очистки | Межпроцессный flock на задание; очистка ждёт завершения I/O; regression отмены во время sendDocument |
| Блокировка была только у worker | Два bot могли повторить отправку и конфликтовать в polling | Отдельная пожизненная блокировка bot; роли не блокируют друг друга |
| Поздний отказ старого статуса мог отменить новый статус и задание | Потеря обработки после изменения состояния | Отказ outbox условен по актуальному payload; regression delayed failure |
| Sender следовал символьным ссылкам внутри рабочего каталога | Отправка другого файла, расхождение с правилами безопасных путей | Проверка regular_path без resolve, запрет symlink у корня и артефакта |
| Пустой TXT имел нулевой размер, который TDLib запрещает загружать | Ошибка доставки результата без речи | На отправку используется один перевод строки, пустая контрольная точка не изменяется; реальный multipart с отказом для нулевого файла и восстановление SQLite проверены |
| Недоверенный Retry-After мог переполнить даты или дать NaN/Infinity | Сбой интерфейса/очереди | Единый парсер конечных представимых сроков, проверка Repository.defer, безопасный показ старого повреждённого срока |
| NAT64 local-use 64:ff9b:1::/48 не был запрещён | Обход проверки адреса при соответствующем маршрутизаторе NAT64 | Запрет обоих стандартных NAT64 префиксов, проверки адресов |
| Глубокий JSON, неподдерживаемый Unicode и нечисловая диагностика могли выйти из модели ошибок | Падение worker вместо ошибки задания | Предел глубины 100, контролируемые ошибки декодирования/UTF-8 и конечные числа пауз |
| Поиск пауз распознавал слова silence_start/end в произвольной диагностике | Неверные границы частей либо исключение | Получение lavfi-метаданных аудиофильтра через stderr при loglevel=error; input dump с названиями не разбирается |
| atrim продолжал декодировать исходник после конца части | Лишняя CPU/дисковая работа на длинных записях | Ограничение вывода точной длительностью, сброс PTS; полный охват отсчётов проверен для WAV и сжатых форматов |
| Все ответы частей загружались до проверки размера результата | Пиковая память росла с суммой больших checkpoint, хотя итоговый JSON уже превышал допустимый размер | Суммарный размер raw ответов проверяется при загрузке; ранний result_size_limit сохраняет контрольные точки; regression проверяет, что следующие части не читаются |
| Локальная квота проверялась после извлечения WAV | Повторное декодирование при ожидании без запроса Groq | Read-only проверка квоты до FFmpeg; повторная атомарная резервация перед API сохранена |
| Bot API getFile использовал короткий сетевой timeout даже для крупного вложения | Ложный отказ при долгом скачивании сервером | Timeout запроса равен настроенному download timeout, отмена корутины сохранена |
| refresh_statuses просматривал всю бессрочную историю четыре раза/с | Нагрузка SQLite росла со всей историей | Миграция 005: dirty_status с триггерами, частичные и обратные индексы |
| Неограниченная очередь служебных ответов и вечный inbox | Рост диска/времени доставки от посторонних сообщений | До 10 pending служебных ответов на чат и 1000 суммарно; задания имеют приоритет перед обычными reply, callbacks сохраняют приоритет; regression flood 1100 чатов; 30-дневная очистка диагностического inbox/reply небольшими порциями; committed offset защищает от старых replay |
| SQLite backup мог бесконечно ждать заблокированный источник | Зависшая эксплуатационная команда | Общий timeout 60 с и ограниченный busy timeout; заблокированная база проверена реальным SQLite |
| Конкурентное первое включение WAL возвращало BUSY вне busy_timeout | Редкий отказ migrate | Ограниченный повтор только SQLITE_BUSY/LOCKED, regression и 300 конкурентных пар |
| SDK принимал GROQ_BASE_URL из неописанного окружения | Передача API-ключа другому серверу | Явный официальный base_url, regression с подставным доменом |
| SQLite при обычном открытии не проверяла symlink базы и sidecars | Выход из доверенного файлового состояния | Проверка базы/WAL/SHM перед открытием |
| Неожиданное исключение библиотеки мог вывести сырую ошибку в CLI traceback | Утечка URL, тела ответа или токена в журнал | Безопасная терминальная диагностика без текста исключения; regression с чувствительной строкой |
| У контейнеров не было пределов RAM/CPU/processes/tmpfs/logs | Исчерпание ресурсов хоста | Compose: bot 512 MiB, worker/API 2 GiB, 2 CPU, 128 PID, tmpfs 256 MiB, ротация логов; FFmpeg 1 decoder/filter thread и max_alloc 256 MiB |
| Python 3.12.12 и системный FFmpeg 5.1.9 / старые библиотеки | Известные CVE парсеров медиа и библиотек | Python 3.12.15 / Debian 13, актуальный snapshot, upstream FFmpeg 9.0.2 с закреплённым SHA-256; у собранного FFmpeg сетевые протоколы отключены |
| В базовом образе оставались pip 25.0.1 и liblzma5 с доступными исправлениями | Известные MEDIUM/LOW pip и security advisory xz-utils | Неиспользуемый runtime pip исключён из обоих образов; liblzma5 закреплён на 5.8.1-1+deb13u2 из security snapshot 9 октября |

Lock-файлы находятся рядом с SQLite и не удаляются при очистке задания:
удаление занятого inode разрушило бы гарантию блокировки. Они не содержат
исходных ссылок, текста или секретов. Смерть процесса освобождает flock.
Права 0600, дескрипторы не наследуются дочерними процессами.

История jobs и все подтверждения preview/TXT/JSON остаются бессрочными.
Очистка диагностических processed_updates не удаляет jobs, chunks или
контрольные точки. Незавершённые операции outbox не удаляются по возрасту.

## Производительность

На синтетической SQLite с 10 000 завершённых заданий, 30 повторов SELECT:
старый поиск статусов — **6,143 мс**, новый — **0,098 мс** на проход.
EXPLAIN QUERY PLAN: SCAN всей jobs заменён выбором по PK и индексам.
Это измерение самого запроса в памяти, а не обещание такого ускорения всего бота.

Точность аудио важнее быстрого seek: повторное декодирование от начала до конца
нужной части сохранено для согласованного ресэмплинга. Декодирование после
нужной границы и при известном ожидании локальной квоты устранено.

- Окончательный полный pytest: **399 passed**, без предупреждений,
  `PytestUnraisableExceptionWarning` считается ошибкой.
- Ruff, uv lock --check --offline, wheel/sdist, compileall и shell syntax прошли.
- Installed-package gates окончательного кода: загрузчики, крупный HTTP getFile
  дважды после очистки, одинаковый SHA-256, сохранение TDLib service DB,

  восстановление ответа без повторного Groq и доставка/очистка прошли.
- После общего ограничения reply все **66** Telegram-тестов прошли.
- Полный `scripts/check_containers.py` окончательных образов прошёл:
  официальный Bot API listener/--local/SIGTERM без сети, пять миграций,
  CLI backup/restore и отказ от перезаписи, bot с 512 MiB, блокировки обоих
  процессов, heartbeat/healthcheck/SIGTERM, совместные тома, download/cleanup/
  restart/media/SDK gates. Все созданные проверкой контейнеры и тома удалены.
- Окончательные Trivy scans обоих образов на всех уровнях прошли; 0 записей
  с доступной исправленной версией. Полные остаточные записи и ID образов — JSON.
- Новым FFmpeg в окончательном образе проверены все 11 форматов спецификации:
  MP3/WAV/M4A/OGG/Opus/FLAC/AAC/MP4/MKV/MOV/WebM, точное совпадение объединённых
  отсчётов с полным декодированием, реальные паузы, первая дорожка видео с двумя
  аудиодорожками, вредоносные названия и MOV
  drefs. Воспроизводимый gate: `scripts/check_media_formats.py generate DIR`
  на host с FFmpeg, затем `verify DIR` в образе с синтетическим окружением,
  read-only mount и `--network none`. Генератор использует только синтетический
  тон и паузу; кодеки с задержкой проверяются против декодирования того же файла.
  Запрет нулевых uploads подтверждён
  [официальным TDLib](https://github.com/tdlib/td/blob/master/td/telegram/files/FileLoaderUtils.cpp#L282).

## Границы проверки

Рабочие сервисы не запускались, .env и секреты не читались и не менялись.
Push и развёртывание не выполнялись. Сетевые обращения аудита использовали
только публичные advisories/источники/базы уязвимостей и реестры контейнеров.
Telegram/Groq живые запросы не выполнялись; тесты используют подставные API.

Живой Telegram >20 МБ / очистка TDLib / повторный getFile остаётся открытой
приёмкой из handoff этапа 6. Синтетический HTTP gate не заменяет её.
