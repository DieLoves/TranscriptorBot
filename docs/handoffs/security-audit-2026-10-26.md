## Проверено, изменений не требуется

- Системные пакеты обоих рабочих образов сверены с Debian Security Tracker
  (данные на 26.10): **0** пакетов с доступным исправлением для trixie.
  Trivy не запускался; сверка выполнена по `dpkg-query` образов.
- FFmpeg 9.0.2 — последняя версия. Deno 2.9.7 — новых advisories нет
  (последнее — июнь 2026, исправлено в 2.7.x/2.8.x).
- yt-dlp запускает Deno с `--no-remote --no-prompt`, без `--allow-net`.
- SSRF/DNS/redirects, пути и symlink, лимиты размера/времени, HTML-экранирование,
  квоты Groq, outbox/revision/generation, очистка Telegram cache — новых дефектов нет.
- Рабочая нагрузка: в простое ~0,5 % CPU на сервис, bot 34 MiB, worker 49 MiB.

## Спорные решения, оставленные для решения владельца

- **«Продолжить» после детерминированных ошибок** (`size_limit`, `duration_limit`,
  `unsupported_source`, `source_authorization`, `invalid_media`). Повтор заново
  скачивает источник и снова завершается той же ошибкой. Спецификация хранит любые
  окончательные ошибки 7 дней, поэтому поведение не менялось.
- **Декодирование от начала записи для каждой части**: суммарно O(n²) по длительности,
  зато точное выравнивание отсчётов. По рабочим данным 1 ч 37 мин обрабатывается
  за 69 с вместе с Groq — заметной проблемы нет.
- **yt-dlp 2026.08.19**: YouTube регулярно ломает извлечение; при первой ошибке
  `source_unavailable` для YouTube обновить yt-dlp отдельным изменением.
- **Python 3.12.16** (security-only, вышел 25.10): Docker-образа ещё нет;
  обновить базовый образ, когда появится тег `3.12.16-slim-trixie`.

## Разбиение на части: замер на реальной записи

Лекция 1 ч 31 мин (MP4/AAC, 5480 с), анализ собственным кодом в образе
(FFmpeg 9.0.2); качество разреза оценивалось по энергии чистого сигнала ±50 мс.

- Чистая запись (фон −81 dBFS): 1756 пауз, все 9 разрезов в паузах. Выбор
  «лучшей» паузы вместо ближайшей измеримой пользы не дал — не внедрялся.
- `silencedetect` сравнивает с порогом каждый отсчёт, поэтому подмешанный
  розовый шум со средним уровнем −42 dBFS скрывает **все** паузы (−46 dBFS — ещё
  1627). Тогда разрез по времени попадал в речь **6 из 9** раз (−19…−30 dBFS).
- Исправлено: энергия 10-мс кадров считается из того же PCM-потока анализа
  (stdlib, `math.sumprod`, +~11 с на 4 ч). Без найденной паузы выбирается самый
  тихий участок ≥0,3 с в том же окне, если он не менее чем на 3 дБ тише медианы
  окна; ровный сигнал сохраняет границу по времени. Production-код на шумной версии:
  **0 из 9** в речи; план чистой записи не изменился байт в байт.
- Groq (≈6 мин аудио, 12 запросов): язык во всех 10 частях — русский, фиксация
  языка не нужна. Части, начатые посреди фразы, распознавались без пунктуации и с
  ошибками («привязан тоже пациент», «сами сами все»). С концом предыдущего текста
  в `prompt` (≤200 байт UTF-8, т. е. ≤224 byte-level токенов): «привязан тоже по
  центру», «сами по себе», «никакой цвет не работает», пунктуация восстановлена.
  Внедрено: prompt вычисляется из сохранённой контрольной точки до резервирования
  квоты, поэтому повтор отправляет тот же контекст.
- Спецификация обновлена в двух местах (резервный разрез, контекст предыдущей части).

## Архитектура

Крупная перестройка не оправдана. Два процесса с общим SQLite (WAL), durable
inbox/outbox, optimistic revision/generation и раздельные блокировки соответствуют
масштабу (до 10 пользователей, одно задание за раз) и уже прошли рабочую эксплуатацию:
20 заданий, включая файлы Telegram до 219 МБ и запись 2 ч 21 мин с ожиданием квоты.
Найденные архитектурные слабости — отсутствие изоляции «ядовитых» update и заданий —
устранены выше. Polling SQLite (0,1–0,5 с) даёт пренебрежимую нагрузку; замена
на уведомления усложнила бы систему без измеримой пользы.
